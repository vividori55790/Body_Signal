# Body Signal 상용화 로드맵

> 목적: 현재 MVP를 실제 배포 가능한 모바일 앱으로 끌어올리고, 개인 건강 기록을 지속적으로 사용하는 구독형 제품으로 검증한다.
>
> 작성 기준: 현재 저장소의 React/Vite + Capacitor 구조, `localStorage` 중심 데이터 저장, 목업 데이터 fallback, Android 빌드 파이프라인을 기준으로 작성했다.

## 1. 현재 상태와 핵심 진단

### 이미 있는 것

- 증상/상태를 기록하고 대시보드·캘린더·히스토리로 보는 핵심 화면
- 다크 모드, PIN 잠금, JSON 내보내기
- Google Calendar 연동 시도
- PWA 산출물과 Capacitor Android 프로젝트
- GitHub Actions 기반 Android 빌드 흐름

### 상용화 전에 반드시 해소할 것

1. **데이터 신뢰성**: 데이터가 브라우저/기기 `localStorage`에만 있고 계정·클라우드 백업·다중 기기 복원이 없다.
2. **데모 흔적**: 데이터가 없을 때 목업 데이터를 주입하므로 신규 사용자에게 실제 기록과 샘플 기록이 섞일 수 있다.
3. **수익화 기반 부재**: 상품, 결제, 구독 상태, 영수증 검증, 환불·해지 처리가 없다.
4. **민감정보 보호 미완성**: PIN은 기기 내 UX 잠금일 뿐 서버 보안이나 복구 정책이 아니다. 건강 데이터의 접근·삭제·보존 정책도 필요하다.
5. **운영 불가**: 오류 추적, 분석, 원격 설정, 고객 문의, 백업 복구, 약관·개인정보 동의가 없다.
6. **의료제품 경계 불명확**: 진단·치료를 제공하는 것처럼 보이면 규제·책임 범위가 급격히 커진다. 초기 포지셔닝은 “건강 기록과 패턴 인사이트”로 제한한다.

## 2. 제품 전략

### 타깃 웨지

초기에는 “반복되지만 병원 진료 사이에는 놓치기 쉬운 신체 신호를 30초 안에 기록하고, 의사와 공유할 수 있게 하는 사람”에 집중한다.

- 1차 사용자: 반복성 통증·피로·두통·소화 불편 등 장기 패턴을 관찰하는 성인
- 구매자 문제: 기록을 시작해도 며칠 뒤 중단하고, 진료 시점에는 날짜·강도·유발 요인을 기억하지 못함
- 핵심 약속: **빠른 기록 → 주간 패턴 이해 → 필요할 때 신뢰할 수 있는 리포트 공유**
- 금지할 약속: 질환 진단, 약물 처방, 치료 효과 보장, 응급 판단

### 핵심 루프

`알림/상황 발생 → 30초 기록 → 누적 데이터 시각화 → 주간 인사이트/리포트 → 다음 기록 동기 강화`

초기에는 AI보다 이 루프의 반복률과 데이터 품질이 우선이다. AI 인사이트는 충분한 데이터와 안전한 설명·근거·면책이 준비된 뒤 제한적으로 추가한다.

## 3. 목표 상태 (출시 기준)

### 사용자 관점

- 이메일/소셜 로그인으로 새 기기에서 기록을 복원한다.
- 오프라인에서도 기록하고, 연결되면 충돌 없이 동기화한다.
- 무료 사용자가 제품의 핵심 가치를 경험한 뒤 명확한 제한과 가치 제안으로 업그레이드한다.
- 월간 리포트를 PDF 또는 공유 링크로 내보내며, 공유 취소와 만료를 제어한다.
- 계정·데이터를 직접 내보내고 삭제할 수 있다.

### 사업자 관점

- App Store/Google Play 결제 상태가 서버에서 검증된다.
- 구독 만료·환불·결제 실패·기기 변경을 일관되게 처리한다.
- 핵심 퍼널(가입 → 첫 기록 → 7일 유지 → 유료 전환 → 해지)을 측정한다.
- 장애·동기화 실패·결제 불일치를 탐지하고 재처리할 수 있다.

## 4. 단계별 실행 로드맵

기간은 1~2인 팀 기준의 상대적 순서다. 각 단계는 앞 단계의 종료 조건을 만족한 뒤 진행한다.

### Phase 0 — 제품/법적 기반 고정 (1~2주)

**목표:** 무엇을 만들고 무엇을 약속하지 않을지 고정한다.

- 사용자 인터뷰 10~15명과 1주일 기록 사용성 테스트
- 핵심 이벤트 정의: `signup_completed`, `first_log_created`, `log_completed`, `weekly_review_viewed`, `report_exported`, `paywall_viewed`, `purchase_started`, `subscription_active`, `subscription_cancelled`
- 무료/유료 기능 경계와 가격 가설 문서화
- 개인정보처리방침, 이용약관, 건강정보 면책, 데이터 삭제/내보내기 정책 초안
- 응급 증상·자해·진단 질문에 대한 안전 문구와 외부 도움 안내
- 브랜드·스토어 설명을 “의료 조언”이 아닌 “개인 기록/패턴 관찰”로 정리

**종료 조건**

- 한 문장 가치 제안과 핵심 타깃이 확정됨
- 이벤트 명세와 데이터 분류(민감/식별/운영)가 승인됨
- 법률 검토가 필요한 항목의 담당자와 완료 기준이 정해짐

### Phase 1 — 신뢰할 수 있는 개인용 제품 (2~4주)

**목표:** 목업이 아닌 실제 사용자가 매일 쓸 수 있는 단일 기기 버전을 만든다.

- 목업 데이터 자동 주입 제거 및 명시적 “샘플 데이터 보기” 버튼으로 분리
- TypeScript 전환 또는 최소한 도메인 타입/검증 계층 도입
- 기록 스키마 버전 관리: `condition`, `log`, `trigger`, `symptomIntensity`, `note`, `recordedAt`, `updatedAt`
- IndexedDB 기반 로컬 저장소와 마이그레이션 도입 (`localStorage`는 설정값 중심으로 축소)
- 입력 유효성 검사, 중복 저장 방지, 편집·삭제·undo, 날짜/시간대 처리
- PIN을 “앱 잠금”으로 명확히 표시하고, 생체 인증은 OS 보안 저장소를 통해 추가
- JSON 내보내기뿐 아니라 가져오기, 백업 파일 버전 호환, 가져오기 전 미리보기
- 접근성: 키보드 포커스, 대비, 스크린리더 라벨, 큰 글자, 터치 영역
- 오류 경계와 사용자에게 보이는 실패 상태 추가

**종료 조건**

- 앱 재시작·오프라인·업데이트 후 기록이 보존됨
- 데이터 삭제/가져오기/내보내기를 테스트로 검증함
- 샘플 데이터가 실제 사용자 데이터와 절대 섞이지 않음
- 핵심 기록 완료율과 첫 기록까지의 시간이 측정됨

### Phase 2 — 계정/클라우드/동기화 (3~6주)

**목표:** 기기를 잃어도 데이터가 사라지지 않는 서비스로 전환한다.

- 관리형 인증 도입: 이메일 magic link 또는 passkey 우선, 소셜 로그인은 보조
- 서버 데이터 모델과 사용자별 접근 제어(RLS/authorization) 설계
- 동기화 큐: 로컬 우선 기록 → 서버 업로드 → 재시도/백오프 → 성공 확인
- `clientId`, `version`, `updatedAt`, 삭제 tombstone을 사용한 충돌 정책
- 로그아웃 시 캐시 정리, 계정 삭제 시 서버·백업·분석 데이터의 삭제 범위 정의
- 동기화 상태 표시와 “마지막 백업 시간”, 실패 재시도 UI
- 서버 비밀키는 클라이언트에 포함하지 않고, 환경별 secret 관리
- 자동 백업, 복원 런북, 데이터베이스 마이그레이션/롤백 전략

**권장 경계**

- 앱: 기록 입력, 오프라인 큐, 화면 렌더링
- API: 인증, 데이터 검증, 동기화, 리포트 생성 요청
- DB: 사용자 데이터와 구독 entitlement의 원본
- 비동기 작업: PDF 생성, 이메일, 분석 집계

**종료 조건**

- Android 실기기 2대에서 동일 계정의 생성·편집·삭제가 수렴함
- 네트워크 단절/재연결, 중복 요청, 앱 강제 종료 시 데이터 유실이 없음
- 계정 삭제와 데이터 내보내기 요청을 운영자가 재현할 수 있음

### Phase 3 — 유지율을 만드는 핵심 경험 (3~5주)

**목표:** 기록 앱을 “한 번 써보는 앱”에서 “다시 열 이유가 있는 앱”으로 만든다.

- 온보딩에서 기록 목적, 개인정보 선택, 첫 기록까지 60초 이내 유도
- 사용자가 직접 빈도·시간을 정하는 알림(기본값은 보수적으로)
- 주간 리뷰: 빈도, 강도 변화, 시간대, 사용자가 선택한 유발 요인
- “상관관계”를 인과관계처럼 표현하지 않는 설명과 표본 수 표시
- 템플릿/빠른 입력, 최근 항목, 자동 저장, 편집 접근성 개선
- 월간 리포트: 원본 기록, 기간, 범례, 누락 구간, 사용자가 추가할 메모
- 의사/상담자 공유 시 최소 권한, 만료 링크, 취소, 다운로드 기록
- 알림 피로도·이탈 이유 조사와 알림 빈도 자동 조정

**종료 조건**

- 코호트 기준 7일차 기록 유지율을 측정할 수 있음
- 인터뷰에서 “다음에도 쓸 이유”가 2개 이상 반복됨
- 리포트가 의료진에게 오해를 유발하지 않는지 사용성 검토 완료

### Phase 4 — 구독 MVP와 결제 운영 (3~5주)

**목표:** 결제 버튼이 아니라 환불·해지까지 포함한 정상적인 구독 상품을 운영한다.

#### 상품 가설

| 구분 | 무료 | Plus(가설) |
|---|---|---|
| 빠른 기록/기본 히스토리 | 제공 | 제공 |
| 보관 기간/기록 개수 | 제한 | 확장 또는 무제한 |
| 기기 동기화/백업 | 제한적 | 제공 |
| 주간·월간 인사이트 | 기본 요약 | 전체 리포트/추세 |
| PDF·공유 리포트 | 제한 | 제공 |
| 데이터 내보내기 | 제공 | 제공 |
| 가격 | 무료 | 월간 + 연간(연간 할인) |

가격과 제한값은 인터뷰가 아니라 실제 결제 실험으로 검증한다. 건강 데이터에 대한 필수 접근·삭제·내보내기 권리는 유료벽 뒤에 두지 않는다.

- Google Play Billing/Apple StoreKit을 플랫폼 규칙에 맞춰 연동
- 서버에서 구매 토큰/영수증 검증, entitlement 원장화
- `active`, `grace_period`, `past_due`, `canceled`, `expired`, `refunded` 상태 모델
- 구매 복원, 기기 변경, 결제 실패, 환불, 구독 해지, 가격 변경 처리
- 웹 결제와 앱 결제를 섞을 경우 플랫폼 정책과 고객지원 경로를 먼저 검토
- paywall은 기능 제한 시점에 맥락 있게 노출하고, 취소 방법·갱신일·가격을 명확히 표시
- 결제 성공/실패·서버 검증 실패를 사용자에게 성공처럼 보이지 않게 처리
- 세금·영수증·환불 문의·스토어 고객지원 책임 분리

**종료 조건**

- 테스트 상품으로 신규 구매·복원·취소·환불·결제 실패를 각각 재현함
- 서버 entitlement와 앱 UI가 불일치할 때 재동기화 가능함
- 구독 상태를 수동으로 조회하고 고객에게 보상/회수할 운영 절차가 있음

### Phase 5 — 공개 출시와 성장 시스템 (4~8주)

**목표:** “출시 가능”을 “운영 가능한 서비스”로 만든다.

- Android closed test → limited public release → 단계적 공개
- iOS 출시가 목표라면 Capacitor 플러그인·StoreKit·심사 메타데이터를 별도 검증
- 랜딩 페이지, FAQ, 개인정보/약관, 문의 채널, 상태 페이지
- Crash/error monitoring, 성능 측정, 결제·동기화 알람, 감사 로그
- CI에서 lint/build/unit/e2e, 서명된 release artifact, SBOM/취약점 점검
- staged rollout, feature flag, kill switch, 원격 설정
- 고객 문의 SLA, 데이터 삭제 요청, 환불 요청, 사고 대응 런북
- 앱스토어 스크린샷·온보딩·리뷰 답변·릴리즈 노트 운영

**출시 게이트**

- P0/P1 크래시·데이터 손실·결제 오류 0건
- 복구 리허설이 목표 RTO/RPO 안에 들어옴
- 개인정보 동의/철회, 계정 삭제, 데이터 내보내기 모두 실제 계정으로 검증됨
- 스토어 심사 정책과 건강 관련 표현을 체크리스트로 승인함

## 5. 기술 목표 아키텍처

### 최소 구성

```text
React + Capacitor
  ├─ Local repository (IndexedDB, offline-first)
  ├─ Auth/session client
  ├─ Sync queue + conflict resolver
  ├─ Analytics consent gate
  └─ Billing adapter (StoreKit / Play Billing)

API
  ├─ Auth and user profile
  ├─ Logs/conditions CRUD with authorization
  ├─ Sync endpoint with idempotency
  ├─ Entitlement endpoint + store webhooks
  └─ Export/report job

Data
  ├─ Primary database with per-user isolation
  ├─ Encrypted object storage for generated reports
  ├─ Queue/worker
  └─ Audit/operational logs with short retention
```

### 데이터 원칙

- 건강 기록은 분석 이벤트와 분리하고, 분석에는 기본적으로 집계·비식별 이벤트만 보낸다.
- 원문 메모는 기본적으로 광고 타깃팅에 사용하지 않는다.
- 모든 서버 쓰기는 인증, schema validation, authorization, idempotency를 거친다.
- 시간은 UTC로 저장하고 표시 시 사용자 시간대로 변환한다.
- 스키마 마이그레이션은 하위 호환 기간과 rollback을 정의한다.

## 6. KPI와 실험 순서

### 제품 지표

1. Activation: 가입 후 24시간 내 첫 기록 완료율
2. Time to value: 첫 기록부터 첫 유용한 주간 리뷰까지 시간
3. Retention: D1/D7/D30 기록 사용자 비율
4. Habit: 활성 사용자 주간 기록 일수와 완료율
5. Data trust: 동기화 성공률, 유실/중복 신고율, 내보내기 성공률
6. Conversion: paywall 조회 → trial/구매 → 유료 유지
7. Business: MRR, ARPU, churn, refund rate, LTV/CAC
8. Quality: crash-free sessions, P95 API latency, 결제 검증 실패율

### 실험 우선순위

1. 기록 입력 단계를 줄이는 실험
2. 알림 문구·시간·빈도 실험
3. 주간 리뷰 형식과 리포트 가치 실험
4. 무료 제한값 실험
5. 월간/연간 가격과 trial 실험

한 번에 하나의 핵심 가설만 바꾸고, 건강·개인정보 관련 문구는 전환율보다 신뢰와 안전을 우선한다.

## 8. 운영 원칙과 하지 않을 것

- 근거가 부족한 패턴을 “원인”이나 “진단”으로 단정하지 않는다.
- 무료 사용자의 데이터 접근권을 결제 실패로 잠그지 않는다.
- 분석 SDK를 동의 없이 건강 원문과 함께 설치하지 않는다.
- 백엔드·결제·보안 기반이 없는 상태에서 광고나 AI 기능으로 규모를 키우지 않는다.
- 하나의 대형 출시보다 작은 cohort를 대상으로 측정 가능한 단계적 출시를 한다.

## 9. 90일 실행안

### 1~30일

- Phase 0 완료
- 로컬 데이터 계층 교체와 목업 제거
- 계정·데이터 모델·이벤트 명세 확정
- 이용약관/개인정보/면책 초안

### 31~60일

- 인증·클라우드 동기화·내보내기/삭제
- 주간 리뷰·알림·리포트
- 오류 모니터링·분석 동의·CI 테스트
- 내부/closed test로 실제 기기 검증

### 61~90일

- 테스트 결제와 entitlement 운영
- 무료/Plus paywall 실험
- 지원·환불·사고 대응 런북
- 단계적 공개 출시와 첫 코호트 측정

90일의 성공 기준은 매출 규모가 아니라 **데이터 유실 없이 실제 사용자가 4주 이상 반복 사용하고, 결제·해지·환불을 운영자가 처리할 수 있는 것**이다. 이 기준을 통과한 뒤에 가격 최적화와 확장 기능에 투자한다.
